# Release packaging

fribblr has published no release. Publishing one (a `vX.Y.Z` tag and a GitHub release at https://github.com/elenaOnline/fribblr) is the owner's decision. Until then fribblr is installed from a checkout (`node /absolute/fribblr/scripts/install.mjs --project /absolute/project`, see [INSTALL.md](INSTALL.md)); such an install records `"source": "checkout"` in the project pin and never checks for releases. The steps below are what a release needs.

Version policy: every release bumps the minor version only, X.Y.0, and is shown to people as X.Y ("fribblr 1.4": release title and notes, README, app UI, update notices, installer and setup output). There are no patch releases. A breaking major release still needs the user's yes, as before. Machinery keeps X.Y.Z: `package.json`, `lib/update-compatibility.json`, the `vX.Y.Z` tag, asset names, project pins and the update comparison. `displayVersion` in `scripts/install.mjs` is the one helper for showing a version (it keeps a non-zero patch from older releases, such as 1.0.4); `fullVersion` lets the installer, setup and `update now --to` accept X.Y as X.Y.0. The version number follows upstream Tinka's, from which fribblr was forked at 1.4.

Package identity: the package name, the app ZIP's root folder and the prefix of every release file are `fribblr` (renamed from upstream's `board-room` on 2026-11-26, before any fribblr release, so no installed copy needed migrating). The installer replaces only an app folder whose `package.json` says `fribblr`; it refuses upstream Tinka's app (`board-room`), so it can never overwrite one.

1. For the 0.5.0 candidate, additionally verify explicit dry-run/apply migration (including raw orphan notes and prior revisions), repeatability, graph operations/conflicts/recovery, resource containment and range serving, cross-instance write identity, and Grid/Canvas plus composite viewer accessibility. Use temporary external fixtures; do not migrate a current project for QA. Public publication and current-project installation require explicit direction.
2. Update `package.json` and version examples as appropriate. Run `npm test`, then `node tests/browser.mjs` for UI changes. Use external fixtures and inspect screenshots.
3. Run `node scripts/package.mjs --out /absolute/external/output`. It refuses existing output files and writes `fribblr-vVERSION.zip`, `fribblr-skill.zip`, standalone `fribblr-install.mjs`, a version-bound `fribblr-vVERSION.compatibility.json`, and a matching `.sha256` sidecar for each. Update `lib/update-compatibility.json` deliberately: exact eligible starting versions, runtime requirements, supported config/workspace schemas, and migration policy must match the release. The compatibility asset binds the app ZIP digest; its embedded counterpart is revalidated during update.
4. Install the app ZIP using the standalone installer into a temporary directory, with no installed skill. Start two independent fixtures, check labels/URLs and notes, replace one installation, and verify the other stays healthy. Create a portable project, commit its complete boards and notes, clone it to a different path without its app/local files, and restore with the checked-in setup script and matching ZIP/checksum. Confirm notes and manifests are unchanged and Git stays clean. Automated tests cover these cases; visual checks separately cover header, footer controls, narrow layout, and preview interactions. Stop only these temporary processes.
5. Review the source and archives for private content. The explicit app allowlist is `README.md`, `LICENSE`, `AGENTS.md`, `IMPLEMENTATION_CONTRACT.md`, `package.json`, `cli.mjs`, `server.mjs`, `public/`, `lib/`, `scripts/install.mjs`, public docs (`README`, `AGENT`, `BOARD`, `PROTOCOL`, `RELEASE`, `INSTALL`), and generic `examples/`, including the compiled whiteboard engine in `public/drawxide/pkg/` (see `public/drawxide/NOTICE.md`). The app ZIP extracts to `fribblr/`. The separate optional skill ZIP extracts to `fribblr/` and contains only `SKILL.md`. The standalone installer is identical to the app's installer. None includes personal boards, notes, configs, runtime state, registry, test output, or screenshots.
6. With publication authorized by the owner, commit and push the reviewed source to https://github.com/elenaOnline/fribblr. Create a version tag and GitHub release with both ZIPs, the standalone installer the compatibility JSON and all four checksums. Use a release-notes file with `gh release create vVERSION ... --notes-file PATH`.
7. Verify the published asset digests, then exercise a fresh installation with the published `fribblr-install.mjs --project /absolute/temporary/project`. This uses the actual latest release for a new project. `--version VERSION` selects a specific tag instead; an existing project's setup restores its pin. Confirm package/receipt version and health, then stop the temporary instance.

Before publishing, a release can be proven against a local folder: build it with `package.mjs`, install the app ZIP into a temporary project with `node /absolute/output/fribblr-install.mjs --project /absolute/temporary/project --zip /absolute/output/fribblr-vVERSION.zip --checksum /absolute/output/fribblr-vVERSION.zip.sha256`, build a next version from a copy of the source, and point the updater at its output with `FRIBBLR_UPDATE_FEED=/absolute/next-output` (`TINKA_UPDATE_FEED` also works). `update check` and `update now` then see that folder instead of GitHub; every other check applies.

Normal installed start checks latest at most once daily; default notify never silently replaces the app. Explicit local auto consent applies only to declared compatible stable releases before a stopped start. There is no updater daemon. Each project's explicit install path and package/receipt pin its installed version. Replacing one app directory does not update another. Public repository visibility does not select an open-source license.

## Rollback

The installer retains an adjacent `.app.backup-TIMESTAMP-ID` directory. If the new install starts but a later manual review finds a problem, stop it with its own CLI and config. Move the new directory aside and move the selected backup into the original app path. Start the restored CLI using the unchanged external config. Retain both directories until verified. The installer performs this swap automatically when installation, restart or health verification fails, restores the prior config/pin, and reports any failed recovery step. A stopped candidate is temporarily started for health and stopped before acceptance; its original config bytes are retained. New INSTALLATION.json receipts include per-file baselines. Old setup helpers remain preserved; deliberate reinstallation with the current standalone installer is needed to establish baselines for future automatic replacement.


Workspace metadata migration is separate from replacing the app. Never enable it implicitly in an installer. Back up workspace metadata, original legacy folders and resource roots before explicit conversion. Rollback of the app does not roll back schema 2 edits: retain the metadata backup and use the compatible candidate, or archive metadata outside its configured workspaceRoot to return to untouched legacy folders. Record these as separate gates in release evidence.

Experience review must include an actual realistic mixed board and complete user
loops, rather than isolated attractive controls: open/edit/re-edit, commit/cancel,
failed-save recovery, comments/votes and return to the same passage or canvas.
Inspect saved small geometry, narrow viewports and real content. Keep rendered
candidate/owner acceptance separate from source tests, package identity and live
health; do not publish a technically passing build while that review is pending.
